# pyjab 长期路线图

> 配套文档：问题清单与分诊见 `docs/TRIAGE.md`；MCP 产品计划见 `docs/PYJAB_MCP_PLAN.md`
> 约束前提：每周可投入 **4–6 小时**；开发机为 macOS，**没有 Windows 环境**（见分诊文档第 7 节）；变现目标为"埋好伏笔"，不追求短期收入。

---

## 1. 现状判断

pyjab 不是一个需要"重新发明"的项目，而是一个**被中断的项目**：

| 事实 | 含义 |
|---|---|
| PyPI 近 6 个月约 16,985 次下载（月均约 2,800） | 需求真实且稳定，甚至在增长（2026-04 的 1,894 涨到 2026-07 的 3,977） |
| fork/star ≈ 48%（25/52） | 用户不是收藏，是把代码改进了生产环境 |
| 最后发版 2022-05，最后提交 2023-05 | 四年空窗，但用户没走 |
| 17 个 open issue/PR，最近 5 个零回复 | 反馈管道断了，不是需求断了 |
| 2 个已写好的 PR 挂着没人合 | 有外部开发者愿意贡献，但没人接收 |

**核心结论**：pyjab 最大的问题从来不是技术，是**没有人接收反馈**。这一点恰好是 AI 辅助最擅长补的（分类、复现、写修复、写文档、发版），所以"现在有 AI 加持"这个判断是成立的。

## 2. 战略定位

### 一句话

> **让 AI agent 和自动化脚本能够操作那些没有 API 的 Java 桌面应用——而且不用改目标应用。**

### 真实护城河在哪里

不是"Python 版的 Selenium"，而是**在 Java 语义层的深度**：

| 方案 | 代表 | 语义深度 | 是否需改目标应用 | 平台 |
|---|---|---|---|---|
| 视觉/像素 | 各类 VLM computer-use | 最浅（靠猜坐标） | 否 | 全平台 |
| 通用 UIA 桥接 | `FlaUI-MCP`（**103 ★**）、`windows-computer-use-mcp`（41 ★） | 中（Java 需经 JAB→MSAA→UIA 两次桥接，表格/文本/选择等 Java 语义会丢失） | 否 | Windows |
| **JAB 外部桥接** | **pyjab** | **深**（直接拿 `AccessibleTable`/`AccessibleText`/`AccessibleSelection`） | **否** | Windows |
| Java agent 注入 | `swing-mcp`（2 ★） | 最深 | **是**（需改启动参数） | 跨平台 |

**pyjab 占据的生态位是唯一的**：语义深度接近注入方案，但**不需要改目标应用的启动方式**。
在企业环境里这条差别是决定性的——生产 Java 客户端的启动参数通常动不了，还会触发安全审查。

### 竞争时间窗

- 通用 Windows 自动化 MCP 已经很拥挤：`FlaUI-MCP` 2026-02 创建、103 ★；`windows-computer-use-mcp` 41 ★；另有至少 8 个同类项目
- Java 专属 MCP **几乎是空的**：`swing-mcp`（2026-07，2 ★）、`java-autopilot`（2026-05，1 ★）
- AWS 正在市场层面推"AI agent 操作 legacy 应用"（WorkSpaces 相关功能）

**判断**：这个空位是真实的，但不会一直空着——通用 UIA 方案正在快速积累用户，一旦有人把"支持 Java"当成一个 feature 加进去，窗口就关了。**窗口期估计 6–12 个月。**

### 最大的未验证假设

> **在真实 Java 应用上，pyjab 的 JAB 直连是否真的比 `FlaUI-MCP` 的 UIA 桥接明显更好？**

这是整个战略的地基，但**目前没有证据**。必须尽早用最小成本验证（见第 6 节 R4 与 `docs/PYJAB_MCP_PLAN.md` 第 2.3 节）。如果答案是"差别不大"，整个 MCP 方向的优先级要下调。

## 3. 三层价值结构

```
第 3 层  支持 / 定制 / 咨询          ← 收入（需要与人打交道，作为上行期权）
         ↑
第 2 层  pyjab-mcp（MCP 能力层）      ← 2026 年的分发渠道，AI agent 的入口
         ↑
第 1 层  pyjab（开源库）              ← 信任、分发、技术底座
```

**三层的关系**：第 1 层是资产，第 2 层是放大器，第 3 层是变现。**不要跳过第 1 层直接做第 2 层**——pyjab-mcp 的质量完全取决于 pyjab 的 DLL 定位、遍历性能、DPI 正确性。地基不修，MCP 层是在流沙上盖楼。

## 5. 许可证决策（必须尽早处理）

### 问题

pyjab 是 **GPLv2**。GPLv2 是**传染性**许可：用户的程序链接了 pyjab，用户的程序也必须以 GPL 发布。

对一个"自动化公司内部老 Java 客户端"的脚本来说，这**不可接受**——公司的内部脚本不可能开源。这就是 2022 年 issue #30 的诉求。

**这不是理论问题**：GPLv2 正在把价值最高的用户（企业 RPA / 测试团队）挡在门外。PyPI 每月 2,800 次下载里，有多少人装上后看到 GPL 就走了，是无法统计的沉默流失。

### 约束

**不能单方面重新授权**。外部贡献者 `jsa34` 有 19–20 个 commit，且触及核心文件：

| 文件 | jsa34 的 commit 数 |
|---|---|
| `pyjab/jabelement.py` | 12 |
| `pyjab/jabdriver.py` | 9 |
| `pyjab/common/win32utils.py` | 6 |
| `pyjab/common/xpathparser.py` | 3 |
| `pyjab/common/service.py` | 3 |
| `tests/*` | 8 |

重写这些贡献不现实。**必须取得他的同意。**（`jsa34@cam.ac.uk`，剑桥，2022 年时活跃。）

### 三个选项

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 维持 GPLv2，卖服务** | 不改许可，靠支持/定制/咨询收费 | 立刻可做，无需任何人同意，完全合法 | 企业采用率被 GPL 限制；竞品可自由取用代码 |
| **B. 改为 LGPLv2.1** | 取得 jsa34 同意后重新授权 | **直接回应 2022 年的合理诉求**；企业可链接而不传染；pyjab-mcp 可用 MIT 发布 | 需要找到并说服 jsa34；已按 GPLv2 分发的旧版本不可撤回 |
| **C. 保持 pyjab 为 GPLv2，pyjab-mcp 独立进程** | pyjab-mcp 通过子进程/管道调用 pyjab，自己不 import | 绕过 copyleft 的常见做法 | **法律灰色地带**，需律师确认；架构上也变复杂 |

### 建议

1. **短期（阶段 0–1）走 A**：不改许可，先把项目救活。发版、回 issue 都不需要碰这个问题。
2. **同时启动 B 的前置动作**：在阶段 1 期间尝试联系 `jsa34`，取得一份明确的重新授权同意（哪怕是邮件确认）。这件事**没有成本，但需要提前做**，因为结果不确定。
3. **如果 B 成功**：pyjab 改 LGPLv2.1，pyjab-mcp 用 MIT/Apache-2.0 发布。变现路径打开（支持订阅、商业版、云服务都可以谈）。
4. **如果 B 失败**：维持 A，并**在 README 里明确、友好地说明 GPLv2 对使用者的实际影响**（而不是像 2022 年那样把提问者驳回去）。诚实说明会挽回一部分用户。

**额外提醒**：2022 年对 #30 的处理方式（"您可能有些误解" → "Close without comment"）本身造成了声誉损失。请求者在技术上是正确的。**无论最终改不改许可，都应该重新以正确的方式回应这个问题。**

## 7. 每周 4–6 小时的现实分配

每周 4–6 小时**不足以同时做维护和开发**。建议的节奏：

| 固定项 | 时长 | 说明 |
|---|---|---|
| issue 响应与分类 | 1 h | **优先级最高，不可跳过**。这是唯一的反馈来源 |
| 当阶段主线任务 | 3–4 h | 只做一件事，做完再做下一件 |
| 发版与收尾 | 0.5 h | 保持"随时可发版"的状态 |

**关于"不沟通"的现实修正**：
issue 回复是异步文本，不是会议或销售电话，属于你想保留的形态。但**完全零交互等于零反馈**——而反馈是你现在最缺的东西。建议把"每周 1 小时回 issue"当作不可协商的固定开销。
